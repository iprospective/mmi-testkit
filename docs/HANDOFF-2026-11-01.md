## 5. Cible `mmi-dev-knowledge` / `mmi-testkit`

### Nom

- Outil et CLI : **`mmi-kb`**.
- Dépôt : `iprospective/mmi-dev-knowledge` ; CLI `mmi-kb` ; projet Redmine `knowledge-base`.
- Projet Redmine : `test-kit`, client `iprospective`.

### Principe

> `mmi-kb` contient les **faits génériques** sur les produits/outils.  
> PM contient la **mémoire d’un projet client**.  
> Les tâches référencent `mmi-kb` ; `mmi-kb` ne référence ni client ni tâche.

- Docs qui définissent un produit (Dolibarr, PrestaShop, Nextcloud, Roundcube, Karl PM) →
  `mmi-kb`.
- CDC/évolution/instance client → PM + wiki Redmine.
- Correctifs et configurations spécifiques client → PM.
- Un cas client abstrait peut être promu en quirk générique.
- Aucun secret, aucune URL d’instance, aucun identifiant client dans `mmi-kb`.

### Contenu

- `tool`, `component`, `version`, `compatibility`, `quirk`, `recipe`, `source`, `license`,
  `vendor`.
- Hooks, triggers, templates, menus, objets, patterns par produit/version.
- Sources officielles (wiki, forum, dépôts, releases, modules) et collecteurs.
- Recettes de test génériques (famille `tests`).

### Vues génériques

`docs`, `tests`, `agents`, `compat`, `catalog`, `releases`, `licenses`, `sources`.

- `docs` → `pm-wiki-sync` / générateur Markdown/HTML.
- `tests` → `mmi-testkit`.
- `agents` → `karl-agent` / PM (contexte compact).
- `compat` → TestKit/PM.
- Pas d’endpoint ni de dossier `redmine` ou `testkit` dans `mmi-kb`.

### Stockage / interface

- Git + YAML + JSON Schema = source de vérité.
- CLI `mmi-kb` : `validate`, `index`, `get`, `resolve`, `quirks`, `compat`, `recipes`,
  `view`, `stale`, `export`, `serve`.
- Index SQLite généré ; API read-only (`/views/{family}`) plus tard ; MCP ensuite.
- `verified` exige une preuve externe et une revue ; `fetched_at`, `verified_at`,
  `verified_by`.

### Double synchronisation PM ↔ Redmine

La synchronisation est **bidirectionnelle** :

- PM est la vue la plus complète et la référence de travail ;
- Redmine peut créer des tâches, de l’historique et des documents wiki ;
- PM importe et réconcilie ; les conflits sont tracés et arbitrés côté PM ;
- `mmi-kb` n’intervient pas dans cette synchronisation.

### Tâches qui alimentent `mmi-kb`

Une tâche PM peut porter :

```yaml
knowledge:
  action: update
  refs: [tool:dolibarr, component:dolibarr/mmiproduct, doc:dolibarr/hooks]
  target: tools/dolibarr/components/mmiproduct/hooks.yml
```

La tâche exige une MR `mmi-dev-knowledge`, vérifie le caractère générique et enregistre le commit
knowledge. `mmi-kb` ne pointe pas vers la tâche.

### Dépôts cibles

- `iprospective/mmi-dev-knowledge` — knowledge, CLI `mmi-kb`, schéma, index, API read-only.
- `iprospective/mmi-testkit` — core + plugins (`plugins/dolibarr`, `plugins/prestashop`, …) ;
  renommage/transfert de `dolibarr/mmi-dolibarr-testkit`.
- `mmidevtools` reste un module Dolibarr.

### Glossaire

`quirk` a été ajouté au glossaire du projet `iprospective/pm-ai-agents`
(`.mmi-pm/docs/glossaire.md`), synchronisé wiki v3. **À ne plus traiter pour l’instant** :
le sujet glossaire est reporté.

### Cockpit

Il existe un **glossaire lisible/filtrable** dans le cockpit (RM2623/2634/2675) : onglet

## 10. Décisions prises

- `mmi-kb` est le nom retenu.
- `mmi-kb` est indépendant de PM ; PM en est un consommateur.
- Pas de vue spécifique Redmine/TestKit dans `mmi-kb` ; vues génériques `docs/tests/agents/…`.
- Docs produit → `mmi-kb` ; docs client/CDC/instance → PM/wiki.
- `mmi-kb` ne référence ni client ni tâche ; la tâche référence `mmi-kb`.
- Synchronisation PM ↔ Redmine bidirectionnelle, PM référence de travail.
- Contenu `mmi-kb` : outils, versions, composants, hooks, triggers, patterns, quirks,
  recettes, sources, licences, éditeurs/communautés.
- Secrets, URLs d’instance et correctifs client exclus de `mmi-kb`.
- Glossaire/`quirk` : reporté ; l’entrée existante reste en place.
